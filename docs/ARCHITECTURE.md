# Wizard Battles engineering foundation

## Decision and ownership

Retain TypeScript and Three.js. The current creative direction calls for procedural art, readable exchanges and practical browser comparisons/captures; neither procedural assets nor seeded simulation requires a renderer migration. Three.js provides camera, lights, geometry, materials and browser rendering already in use. No concrete engine blocker was found. The simulation imports only Three's standalone Vector3 math module through `math.ts`; its transitive graph creates no scenes, cameras, meshes, materials, geometries or particles. This boundary is checked in tests.

`World` owns contestants, active mechanics, copied arena bounds, a simulation clock, Mulberry32 gameplay RNG, recent semantic events and its telemetry destination. Time advances at the start of each validated `update(dt)` and events receive that time. Browser and default harness use `SIMULATION_DT = 1/60`; simulation dt is part of run identity. Determinism promises apply to the same source/configuration, seed and tick sequence, not arbitrary dt values. There are no process-global clock, RNG overrides or telemetry singleton. Multiple worlds may step in any order.

`BasicWizard` owns movement/resource/casting state and composes tactic rosters, spell factories, modifiers and event/handler pipelines. `contestants/movement.ts` holds default movement profiles; each wizard copies profiles plus experiment overrides. `contestants/aim.ts` computes predictive lead and seeded aim noise. Decisions, cast acceptance/refusal/release/cancellation, movement state changes, dashes, impacts, field interactions, damage and deaths emit semantic telemetry. Telemetry receives copied records and explicit per-world timestamps. It observes simulation; scoring/evaluation must never write back to mechanics.

`spells/` owns projectile motion, collision/damage, emission/homing, timed AOE, melee, blink and slow fields. A frozen spell has no authoritative effect until release. AOE markers and timing derive from that state. Serializable visual descriptions in spell specs are style hints, not graphical objects or a dependency on a renderer. Factories/modifiers are declarative reusable composition, not a plugin engine. See [SPELL_STATE.md](SPELL_STATE.md) for exact state/event contracts and intentional mechanic corrections.

`presentation/BattleView` observes a particular world and owns dynamic Three objects, status bars, telegraphs, trail history and transient effects. `renderer.ts` owns WebGL/camera/lights; `arena.ts` owns arena graphics. Rendering may happen zero, one or many times per tick. Particle randomness derives from visual seed and event sequence, and particle positions from simulation event age; rendering never advances gameplay or consumes gameplay RNG. `recordTick()` records bounded path history independently of rendered frames. Multiple views may observe one world, or separate worlds.

## Scenarios and experiments

`createScenario(options)` is shared by browser and batch runner. It creates fresh wizard/tactic instances. `four-wizards` is the default; `duel` uses red and blue. `rotation` rotates starting positions/facing in radians. The named variant registry currently contains only `baseline`; unknown scenario/variant identifiers fail. Add pilot variants here so batch and browser cannot drift. TypeScript callers can supply per-wizard `movement`, `spellbook` and `modifiers` overrides through `options.wizards`. Spell factories remain the reusable extension point for new mechanics. Gameplay mutation belongs to simulation configuration and code; visual options belong to BattleView.

The harness records scenario, seed, variant, rotation, dt, sample rate and outcome in metadata. Omitted seed means deterministic seed 1; CLI sweeps increment an explicitly supplied seed. Use explicit seeds and unique output directories for experiments. Wall timing and started/ended timestamps are diagnostic and intentionally excluded from deterministic comparisons. `JsonlSink` is node-only; browser imports do not pull filesystem code.

The browser uses a fixed-step accumulator; a slow frame may delay wall-time playback, but cannot change the sequence of simulation decisions. `window.battle` supports deterministic replay/seek and capture. See [CAPTURE.md](CAPTURE.md) for exact commands, artifact identity and temporal history. Browser WebGL validation requires Chromium system libraries from the Carthage Dockerfile.

## Baseline changes and limits

Old seed outcomes are intentionally invalid: the old harness replaced Math.random globally, and mesh/particle construction consumed values from the same stream as tactics/aim. New worlds use independent full-width Mulberry32 streams; effects never consume them. Initial tactic directions/wander are sampled from that world's RNG. Browser timing/cooldowns now follow simulation time. A fresh baseline must be recorded for comparisons.

Other deliberate corrections: instant emission releases the complete burst in one tick, slow fields stack/release independently and match visible dome height, blink honors per-world bounds, and ground-target projectiles land at the marked endpoint instead of overshooting from launch offset or incidental collisions. The charging AOE preview follows predicted aim; release locks its exact endpoint. Effect/fade objects no longer occupy the authoritative spell list. Appearance has been simplified into reusable procedural models/effects; old mesh-only melee lunge never changed collision and remains a visual concern.

This pass does not introduce ECS, universal VFX, a generic engine, complete state serialization or full event sourcing. The recent event buffer is two seconds, not a replay log. Replay reconstructs fresh state from the initial scenario and steps forward, retaining 0.2 seconds of trail history. Long-run checkpoint persistence would need AI/tactic/cooldown/RNG state as well as recent events/history; telemetry frames alone cannot restore a match. Discrete per-tick collision remains, so very large dt can tunnel. Balance and spectator enjoyment are not established by determinism or successful builds. The comparison viewer, batch evaluation/reporting and creative pilot remain downstream work (w6ah-1p0q, z8kh-x168, 9q8g-86g3).

## Verification

`npm test` runs meaningful spell-mechanic, seeded repeat, interleaved-world, import-boundary, telemetry-observation, render-schedule and temporal-effect checks. `npm run build` typechecks and builds the browser. For a headless sweep: `npm run sim -- --runs 20 --max 1800 --seed 1 --runs-dir /tmp/foundation-sweep -q`. Browser capture and visual review are separate acceptance checks; Node scene tests do not prove WebGL/browser operation.
